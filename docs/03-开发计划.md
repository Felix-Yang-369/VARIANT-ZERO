# 开发计划与验证

日期：2026-09-05

下列工时是单人开发、使用占位美术的粗略估算，不是交付承诺；首次原型完成后重新估算。用户已选择同时制作进化与杂交，两套机制分阶段验证。

## 1. 里程碑

| 阶段 | 交付 | 预计专注工作量 | 完成条件 |
| --- | --- | --- | --- |
| M0 方案 | 需求、技术方案、开发任务 | 本轮已产出草案 | 范围与假设可审阅 |
| M1 基础战斗 | 工程、棋盘、阳光、种植、射击、敌人、胜负 | 3–5 人日 | 1 个关卡能从开始玩到胜负并重开 |
| M2a 进化验证 | 2 种植物 × 2 个进化分支 | 2–4 人日 | 升级规则正确，能体现不同策略 |
| M2b 杂交验证 | 3 个固定配方、双材料选择与融合预览 | 2–4 人日 | 融合扣费与材料消耗一致，非法操作无损失 |
| M3 内容完整 | 6 植物、4 敌人、3 关、教学与本地存档 | 3–5 人日 | 3 关可连续通关，解锁和刷新正确 |
| M4 表现与验收 | 统一画风、音效、反馈、适配与修复 | 3–6 人日 | 功能验收及桌面浏览器检查通过 |

合计暂估 13–24 人日；原创逐帧美术、更多杂交配方、原版程序修改、手机适配另估。首版限定 13 种植物形态，不支持任意配对。

## 2. 首轮可直接执行的任务

1. 建立 TypeScript + Phaser + Vite 工程，锁定版本，配置启动和构建命令。
2. 实现画布缩放、5×9 网格和输入坐标转换。
3. 实现固定时间步战斗模型、阳光状态和种植命令。
4. 实现阳光花、豆射手、护盾果，以及普通和护甲敌人。
5. 实现索敌、子弹扫掠碰撞、啃咬、死亡清理。
6. 配置一个测试关卡，加上防线车、胜负与重开。
7. 加入暂停和窗口隐藏处理，完成关键规则验证。
8. 记录试玩问题，调整基础节奏，再进入特色机制开发。

第一轮结束应提供：可运行原型、操作说明、实际验证结果、已知问题；不能只交一张静态游戏页面。

## 3. 验证策略

战斗规则用自动化测试验证关键边界：不足资源的种植不改变状态、阳光仅收集一次、高速子弹不漏判、单位死亡不重复结算、防线车一次性使用、胜负优先级、暂停不推进模拟、升级保留血量比例、融合材料中途死亡时不扣费、合法融合只执行一次、禁止递归组合。

浏览器人工走查完整流程：开始 → 布阵 → 暂停 → 继续 → 胜负 → 重试 → 返回菜单。验证窗口缩放后的点击定位、音频启动、后台恢复及存档异常。每条记录环境、操作、预期与实际结果。

性能验收使用固定场景和种子，记录测试设备、浏览器、敌人/子弹峰值、平均 FPS 与明显卡顿。重开 20 次后检查实体数量、监听器与内存是否持续增长；压力目标见需求文档。

试玩平衡记录：首次种植时间、首次受压路线、关键植物使用率、进化选择率、失败时间与原因。至少人工验证每关存在可通关策略；目标体验是理解规则后可通过，不要求玩家背固定操作序列。

## 4. 风险与处理

| 风险 | 早期信号 | 处理 |
| --- | --- | --- |
| 范围膨胀 | 首关未完成就持续加植物和模式 | 新点子记入后续列表，先完成 M1 |
| 数值失衡 | 固定一种植物即可通关所有关卡 | 调整资源与敌人组合，用关卡体现不同职责 |
| 进化或杂交没有价值 | 升级总比多种一株差或始终最优 | 比较单位资源收益，设计对应的压力情境 |
| 美术拖慢开发 | 动画未完成导致战斗无法验证 | 先用占位资产，冻结尺寸后替换 |
| 浏览器兼容 | 音频不播、缩放误点或后台跳时 | 在 M1 就用 Chrome 与 Safari 验证 |
| 用户实际想修改原版 | 指定原版 EXE、手机版安装包或特定改版 | 停止沿用独立开发假设，按具体版本评估 |

## 5. 后续候选

按试玩结果再选择：新植物、新敌人、更多地图、更多杂交配方、局内随机强化、无尽模式、关卡编辑器、手机横屏。每次只扩展一类主要系统，并补充相应规则与验收条件。
